Software Verification · Reliability Engineering · Case Study

GateGuard

A deterministic verification harness that catches a subtle scoring defect: a rule labeled as a hard stop could still leave a non-zero decision score.

View GitHub PR View Repository

The problem

Decision systems often combine multiple signals into one composite score. But some conditions are not preferences — they are gates.

In this role-scoring engine, posting liveness and timeline feasibility are intended to behave as hard stops. A closed gate should make the decision composite exactly zero regardless of how strong the other scoring signals are.

The implementation could identify a gate as closed while still retaining a small positive composite. For an international student or early-career technical worker deciding which roles are actually actionable, that creates an information asymmetry: the interface can say “closed” while the arithmetic still behaves as though the condition were merely another weighted vote.

Engineering question: Can we prove that every scorer-classified closed liveness or timeline gate actually forces the final composite to zero?

What I built

I built GateGuard, a dependency-free Node.js verification harness that runs controlled fictional scenarios against the real role scorer and checks the resulting composite values against an explicit hard-stop contract.

All test fixtures are controlled and fictional. No real candidate, employer, immigration, sponsorship or private personal data is required.

The defect

Residual-score behavior

A positive gate factor inside the scorer's closed range could still participate in multiplication and leave a non-zero composite.

The scorer could therefore classify the gate as closed while the arithmetic retained residual decision value.

Hard-stop behavior

After identifying a closed gate, the final composite is explicitly forced to zero:

const composite = closedGate ? 0 : multipliedComposite;

Measurable result

The strongest evidence was not simply that the corrected code passed. I deliberately reintroduced the targeted defect in an isolated temporary scorer and confirmed that the harness failed.

26 / 26 registered production checks passed across baseline and boundary suites
5 / 10 baseline checks still passed after deliberately disabling the hard stop
8 / 16 boundary checks still passed after deliberately disabling the hard stop

Production behavior: 10/10 baseline and 16/16 boundary assertions passed.

Deliberate regression behavior: baseline fell to 5/10 and boundary fell to 8/16. Both mutant runs returned process exit code 1.

This is a targeted regression experiment, not a claim of model accuracy or comprehensive mutation coverage.

Boundary behavior

Boundary tests were designed around the configured gate_zero = 0.05 threshold. 

0.0500  → closed gate → composite 0
0.0501  → open control → composite 0.0293

Maximum scoring votes + closed liveness → composite 0
Maximum scoring votes + closed timeline → composite 0

This verifies that the configured boundary is implemented consistently in the registered scenarios and that high vote strength cannot rescue a scorer-classified closed gate.

Verified vs. inferred

Verified by execution

  • PASS / FAIL / ERROR counts
  • Composite outputs
  • Process exit codes
  • Boundary behavior
  • Targeted mutation detection
  • Production scorer remained unchanged during mutation testing
  • Repository privacy and conformance checks

Not established by GateGuard

  • Whether 0.05 is the correct business or policy threshold
  • Whether a real job posting is live
  • Whether an employer will sponsor a candidate
  • Real immigration or work-authorization feasibility
  • Correctness of the full scoring model
  • Whether maintainers should merge the contribution

Failure modes I designed for

Contract violation

A gate is classified as closed but the final composite remains non-zero.

Boundary regression

Exact-threshold values stop behaving consistently with the declared closed-gate contract.

Vote rescue

Strong fit or sponsorship values incorrectly overcome a closed hard stop.

Fixture or contract drift

Tests and declared semantics diverge as the scorer evolves.

What the machine could not know

GateGuard verifies software behavior against a declared contract. It cannot determine whether the contract itself represents the correct real-world policy.

It cannot independently know whether a posting is truly active, whether an employer will sponsor a specific person, whether an immigration timeline is feasible, or how malformed inputs should be interpreted without an explicit policy.

That distinction matters: software tests can prove that a system follows its rules. They cannot prove that the rules are true about the world.
