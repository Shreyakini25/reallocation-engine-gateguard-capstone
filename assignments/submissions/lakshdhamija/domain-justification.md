# Domain Justification — case-cv-integrity-backend-h1b

**Who uses this, and in what exact situation.** An international backend/platform engineer (F-1, MS in Computer Software Engineering, graduating August 2026, OPT starting September 2026, H-1B sponsorship required) who keeps one attested base record (`private/resume.json`, built and attested in the setup exercise) and uses an LLM to tailor a variant per application. Applying at volume under a 90-day unemployment ceiling, the tailoring step is automated — which is exactly where the LLM is most useful (re-emphasis is real work) and most dangerous (the easiest way to "match" a job description is to quietly add things that are not true).

**The information asymmetry.** In a polished, LLM-tailored résumé, the applicant cannot see which lines drifted from their defensible record. A fabricated line does not look fabricated: an added tool reads exactly like a true skill. A recruiter's six-second skim cannot see it either — but an interviewer catches it instantly, the moment they ask the candidate to go deep on a claim they cannot defend. The gap is on the applicant's own side: you ship a claim you cannot defend *without knowing you did*. This mode closes that gap mechanically, before send, by making every un-anchored claim visible and forcing a decision on each.

**Engine layer.** Job-Ops — the application-pipeline integrity family. A fabricated résumé claim is the same species of defect as a dead job link or a stale tracker row: something that looks fine and silently costs the opportunity. The recipe sits between tailoring and the existing render step (`npm run resumes:pdf`), as a gate: exit 0 renders; exit 1 blocks. It also consumes the setup exercise's personal data layer directly — the attested `resume.json` is the source of truth it anchors to, and the checker refuses to run against an unattested base (an unattested extraction is fluency verified against fluency).

**Failure modes specific to this domain.**

1. **The true-but-undocumented addition, mechanically indistinguishable from a fabrication.** Tailoring for a backend role, the LLM expands generic "AWS" into "AWS (EC2, S3, Lambda, RDS, CloudWatch)". Those may be true for this applicant — but they are new tokens absent from the base, identical in form to invented ones. A tool that auto-cut them would delete real, relevant experience; one that auto-kept them would ship fabrications. Either automatic policy is wrong in one direction on every run, which is why the design forces a human DROP/PROMOTE per flag (P1). The live run demonstrated the subtle version: the check flagged `ClickHouse` on a real variant — true experience that the attested base had accidentally dropped during extraction. The flag was not a lie in the variant; it was a hole in the base. Hardest to catch for exactly the person it damages: an applicant who believes their attested record is complete.

2. **The plausible micro-fabrication that survives both a reread and a naive check.** The dangerous case is a single invented technology shaped like the applicant's real stack — e.g. base text containing "etc." becoming "Kubernetes with **etcd** for cluster coordination": one character, a real Kubernetes datastore, invisible on a résumé its owner has reread fifty times. A substring check *also* misses the reverse trap: `rds` inside "dashboards" would falsely anchor a fabricated `RDS`. The substring trap is demonstrated directly in the worked run ("dashboards" is in the sample base; `RDS` still flags); the `etc.`→`etcd` swap is the illustrative shape of the error — in the fixture, `etcd` is caught because it is absent from the base, which is the only anchor test that matters. Both traps are why the matcher is word-boundary and abbreviation-aware rather than a quick grep. This error is hardest to catch for a first-generation international applicant with few interview shots and sponsorship riding on each one — the interview is precisely where it detonates.
